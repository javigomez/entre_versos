### Global Constraints

- No cambiar guion, respuestas correctas ni diseño general.

- Mantener React 19.2.3 y React Native 0.86.3. No actualizar la app para resolver problemas de instalación de los tests.
- No usar snapshots de árboles enteros, sleeps reales ni un servidor web en la suite habitual.
- No considerar `scrollTo` llamado como prueba de que el navegador ha pintado correctamente.
- Mantener la accesibilidad, el orden del guion, el guardado serializado y la confirmación de reinicio.
- No modificar recuperación exacta, navegación «Volver», contenido pedagógico ni estilos ajenos al requisito.

### Decisiones cerradas para el implementador

1. La respuesta del jugador es el ancla hasta su siguiente acción. Los mensajes posteriores del maestro no sustituyen esa ancla.
2. El siguiente botón no tiene que quedar visible. Si no cabe, se alcanza manualmente.
3. Un gesto manual cancela el seguimiento automático, aunque vuelva a dejar el scroll cerca del final. Solo una acción explícita puede reactivarlo.
4. En un error aparecen de nuevo las cuatro opciones después de finalizar el feedback. No añadir otro botón «Reintentar».
5. El recorte es el del viewport. No añadir `numberOfLines`, elipsis ni tamaños de fuente adaptativos para hacer caber la respuesta.
6. Reutilizar la señal ↓ como acceso explícito al contenido inferior. Solo aparece si hay contenido real debajo, no por el espacio auxiliar. Pulsarla permite bajar voluntariamente y deja desactivado el seguimiento automático hasta la siguiente respuesta del jugador.
7. Con movimiento reducido se conserva el mismo protocolo de eventos, pero la pulsación y el desplazamiento pueden completarse inmediatamente y el texto aparece completo.
8. «Maestro, estoy listo.» conserva su función actual de inicio y da paso al primer «Continuar». No crear una respuesta ficticia con ese texto ni consumir el primer turno del jugador. UX-001 gobierna la transformación de Continuar y las opciones.
9. Duraciones iniciales de implementación: feedback 80 ms, ascenso 240 ms; conservar inicialmente 3 caracteres/24 ms de escritura. Son parámetros ajustables, no requisitos inmutables ni tiempos reales que deban esperar los tests.
10. Si el jugador arrastra durante la transición, su gesto prevalece. La selección se acepta una sola vez y se convierte en respuesta, pero no se vuelve a colocar automáticamente arriba.

### 4.1 Coordenadas y firmas obligatorias

Todas las posiciones de esta capa se expresan en coordenadas verticales del contenido del ScrollView, no de la ventana. `viewportHeight` excluye cabecera y safe area. `topInset` es el margen interior de conversación (actualmente 10). `realBottom` incluye mensajes, controles y aviso de guardado realmente montados; excluye el spacer y el overlay transitorio. `cursorBottom` es la parte inferior del texto revelado del mensaje activo, no el final de todos los controles.

export type FollowInput = {

  viewportHeight: number;
  cursorBottom: number;
  anchorTop: number;
  topInset: number;
  bottomInset: number;
  following: boolean;
};
export function anchorOffset(anchorTop: number, topInset: number): number;
export function followingOffset(input: FollowInput): number | null;
export function spacerHeight(realBottom: number, viewportHeight: number,

## 5. Tarea 4 — Reducer de conversación con callbacks identificados

**Archivos:** src/screens/conversationFlow.ts, tests/unit/conversationFlow.test.ts.

### 5.1 Tipos e invariantes

```ts
import type { Session } from '../types/content';
import type { Message, Progress } from '../engine/session';
export type Phase = 'writing' | 'waiting-start' | 'waiting-student'
  | 'waiting-choice' | 'pressing' | 'moving' | 'placing' | 'finished';
export type PendingReply = {
  nextProgress: Progress;
  nextMessages: Message[];
  messageId: string;
  controlId: string;
};
export type FlowState = {
  progress: Progress;
  messages: Message[];
  revealed: number;
  phase: Phase;
  token: number;
  anchorId: string | null;
  pending: PendingReply | null;
};
export type FlowEvent =
  | { type: 'START' }
  | { type: 'ACTIVATE_STUDENT'; controlId: string }
  | { type: 'ANSWER'; controlId: string; optionId: string }
  | { type: 'PRESS_DONE'; token: number }
  | { type: 'MOVE_DONE'; token: number }
  | { type: 'PLACED'; token: number }
  | { type: 'MESSAGE_DONE'; token: number; messageId: string }
  | { type: 'RESET' };
export function createFlow(session: Session, progress: Progress,
  restored: boolean): FlowState;
export function reduceFlow(session: Session, state: FlowState,
  event: FlowEvent): FlowState;
```

- `revealed` cuenta mensajes COMPLETADOS. En writing se monta además `messages[revealed]` animándose. En espera se muestran solo los completados. En placing se monta también la próxima respuesta, todavía oculta visualmente, para medirla.
- `messages` es la lista disponible del motor; no significa que todo esté ya visible.
- `token` es un contador monotónico por instancia. Incrementar al aceptar una nueva interacción, al avanzar a otro mensaje y al resetear. Un callback lleva el token capturado al crearse; si ya no coincide, se ignora.
- `anchorId` cambia al colocar una respuesta del jugador. MESSAGE_DONE de un maestro nunca reemplaza esa ancla. Si no hay jugador todavía, usar ID del maestro inicial.
- Todo evento fuera de su fase o con token/ID incorrecto devuelve el mismo state sin efectos.
- El reducer no hace scroll, no usa fechas, no guarda datos ni ejecuta callbacks.

### 5.2 Función interna de avance

Tras inicializar, START o MESSAGE_DONE, calcular siguiente fase en este orden:

1. Si `revealed < messages.length`: si el siguiente mensaje es player con action, `waiting-student`; en cualquier otro caso `writing`.
2. Si no quedan mensajes y progress.started es false: `waiting-start`.
3. Si no quedan mensajes y todos los retos están completados: `finished`.
4. En otro caso: `waiting-choice`.

`createFlow(..., restored=false)` comienza con revealed=0. Con `restored=true` conserva la política actual de mostrar completos los mensajes reconstruidos; esta tarea no redefine recuperación. La carga inicial decide restored a partir de un progreso restaurado con started=true, igual que hoy. En una sesión restaurada, después del primer layout completo, conservar el posicionamiento inicial actual al final real una sola vez; no usar el spacer para calcular ese final. Después no seguir automáticamente hasta una nueva acción explícita. En sesión fresca comenzar en offset=0. No guardar phase/token/pending/anchorId en AsyncStorage.

### 5.3 Tabla de transiciones a implementar literalmente

| --- | --- | --- |
| waiting-start + START | started=true, reconstruir messages, calcular fase | No fabricar burbuja del texto del botón de inicio. |
| waiting-student + ACTIVATE_STUDENT | Capturar próximo mensaje en pending, token++, pressing | No mostrar jugador ni maestro nuevo. |
| waiting-choice + ANSWER válido | Calcular nextProgress con answer; nextMessages con messagesFor; capturar primera respuesta añadida, token++, pressing | No persistir el intento todavía ni sustituir la parrilla. |
| pressing + PRESS_DONE(token) | moving | No escribir. |
| moving + MOVE_DONE(token) | Aplicar pending.nextProgress/messages, fijar anchorId=pending.messageId, placing | No iniciar maestro; la burbuja se mide oculta. |
| placing + PLACED(token) | writing, pending=null | No marcar el mensaje como completado. |
| writing + MESSAGE_DONE(token, ID activo) | revealed++, token++, calcular siguiente fase | No completar dos mensajes ni saltar un student con action. |
| cualquier estado + RESET | Progreso inicial, mensajes iniciales, revealed=0, token anterior+1, ancla inicial y sin pending | Ningún callback antiguo puede actuar. |

Pending de un student conserva progress y messages actuales. Pending de una opción toma messageId de nextMessages[state.revealed]; verificar que es player sin action. Si no se cumple, es error de integración del motor: test fallido, no incrementar revealed para ocultarlo.

export function createControlledViewport() {

  const placements: { messageId: string; token: number; done: (token: number) => void }[] = [];
  const controller: ViewportController = {

### Comprobación de que las pruebas detectan errores reales

Hacer temporalmente estas mutaciones, una por vez, sin confirmarlas ni tocar cambios ajenos. Ejecutar el test indicado, comprobar FAIL, restaurar exactamente el cambio y volver a comprobar PASS:

Si una mutación pasa, la cobertura correspondiente no está cerrada: reforzar su aserción antes de seguir. No es necesario añadir una herramienta de mutation testing para estas siete comprobaciones acotadas.
